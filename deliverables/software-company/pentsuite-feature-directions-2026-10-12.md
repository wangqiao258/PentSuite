# PentSuite/PentDB 功能优化方向讨论稿（2026-10-12，产品视角 · 只读分析）

> 口径：产品价值判断，非技术债清单（R6/R7/N1/N2 等修复走 bugfix 渠道，本文只在与功能决策相关处引用）。
> 实证基线：2026-10-12 评审报告（pentsuite-code-analysis-2026-10-12.md）+ 本次抽查复核。

---

## 0. 结论先行

1. **产品的价值不是"能扫"，而是 AI 代驾下的「纪律层 + 记忆外挂」**：扫描能力 AI 裸 shell 都有，PentDB 的不可替代性是——每个 finding 必须带可重放报文、每个测试必须归因、AI 不得代批、全库 append-only 留痕。事实层已被真实使用验证（实库 9 项目 / 4271 条观测 / 317 次人审 / 34 条豁免）；**血缘层是最大且最贵的未验证赌注（intents/plan_steps/hints 三表 0 行，N9）**。
2. 功能链五站：**门禁站是护城河（勿动）**；断点在两处——「探测→测试转化」（probe 观测进得来出不去）和「复盘站从未有过数据」。
3. 推荐 Top 3：**血缘层投产实验 → 复测工作台深化 → 探测观测双出口（晋升 + 变化检测）**。
4. 旗帜鲜明不做：kb 语义搜索/本地 LLM、多项目横向对比、移动端、全式报告模板引擎。单用户产品，防范围蔓延比堆功能重要。
5. 附加产品判断：王桥求职转型中，**PentDB 本身即其工程能力 showcase**——血缘层的"AI 跨会话记忆"叙事和报告门面有超出日常效用的附加价值，排序时应加权。

## 1. 核心价值主张与真实使用场景

### 1.1 谁在什么环节用它

- **唯一用户**：王桥，单用户工作站。**AI 代驾**（skill SOP 驱动 CLI 执行），人只做人审/复测/豁免确认/出报告四类动作。
- 人的真实工作量锚点：317 次 review、34 条 waive——**人审与复测是产品的主要人机界面**，不是探测。

### 1.2 功能链各环节实证状态

| 环节 | 现有武器（代码锚点） | 实证状态 | 产品判断 |
|------|------|---------|---------|
| 探测 | `recon.py`（被动子域）；`probe-import`（dirscan/gobuster/ffuf 解析，pdb_assets.py:290-308，入口 :399-422） | 在用；probe scope 硬编码 `"in"`（pdb_assets.py:391） | **用了半截**：进得来、出不去 |
| 入库 | `add`/`exec` 单通道、append-only、DB 层审计触发器 | 4271 条事件，主力通道 | 健康 |
| 门禁 | `lint`（pentdb.py:155-343）+ journal 对账 + 豁免三态 | 211 测试守护、真拦截 | **护城河，勿动** |
| 复测 | finding 详情页复测工作台；`/api/retest`（server.py:507-548）+ lifecycle 自动联动 | 雏形完整 | **缺"轮次"组织**：N 个 finding 的交付前复测靠 suggestion 自由文本 |
| 沉淀 | `kb add→approve→脱敏`；`report --out kb-draft` | 流程在；BM25 检索（kb.py:248-265） | **回路未闭合**：经验只在查询时被消费，没回流到探测/测试策略 |
| 复盘 | intent/plan/hint（pdb_intents.py）+ plan review 图级复盘（须 --refs 引证据） | 三表 0 行（N9） | **从未运行**：复盘层没有可复盘的数据 |

### 1.3 "建了没用"与"用了半截"

| 对象 | 状态 | 产品判断 |
|------|------|---------|
| intents/plan_steps/hints | 0 行 | 最新最重赌注未验证——**先验证再谈扩建**，这是全部方向里优先级最高的动作 |
| pending_tests / stages_enabled / raw_events.stage | 死表死列（R9） | 纯技术清理，走 bugfix 渠道，不占功能预算 |
| SOP 面板页 | 已退役为 AI-only | **正确的降级先例**：提示层不该占人的界面——为血缘层可能的降级提供先例参考 |
| probe 观测层 | 有入库、有面板展示、无出口 | 半截——晋升与 diff 是现成出口（§2 D3） |
| kb | 写入流程重、检索弱、复用回路开着 | 半截——但**先别上 LLM**（§4） |

## 2. 功能优化方向（7 个）

### D1 血缘层投产实验（下一个真实项目强制启用，带验收闸门）
- **一句话**：不写新功能，把 intent 挂接/plan next/hint 注入做成下一个真实项目的强制工作流，用生产数据验证或证伪这套设计。
- **用户故事**：作为独自作战 + AI 代驾的测试者，长项目跨周、每轮全新会话开局，我要在 30 秒内回答"这个方向为什么测、测出了什么、下一步干嘛"——不重复测、不漏测、方向死了敢于弃。
- **与现有功能关系**：增强（使用方式固化 + 小幅降摩擦，如 `intent add` 交互精简）；不新开功能。
- **收益 vs 成本**：收益 **高** / 成本 **低-中**（几乎不写代码，主要是 skill 流程强制化与摩擦打磨）。
- **风险/前提**：0 行本身可能是"设计过重"的信号——若推着一个完整项目仍跑不动，就是证伪，要敢按 SOP 面板页的先例降级。前提：有下一个真实项目。另注意晋升 bug 教训（ready≠done）已被测试覆盖，投产时观察真实负载。

### D2 复测工作台深化（复测轮次：选批→逐条过→轮次汇总）
- **一句话**：从"单 finding 详情页手工复测"升级为按轮次组织的复测流水线，轮次结论汇总自动进报告。
- **用户故事**：交付前我要对 30 个 confirmed finding 组织一轮复测——选一批进本轮、逐条重放报文+一键落 lifecycle、最后出一张复测结论汇总表直接附报告。
- **与现有功能关系**：增强：`/api/retest`（server.py:507-548）、lifecycle 机读词联动、复测时间轴均已在，缺的是"轮次"这个组织概念。
- **收益 vs 成本**：收益 **高**（复测是渗透交付最后一公里，也是人工投入最大环节）/ 成本 **中**。
- **风险/前提**：低，纯增量。前提：实库 confirmed finding 基数决定价值量级。

### D3 探测观测双出口：endpoint 晋升通道 + 两次扫描 diff
- **一句话**：给 probe 观测层（现"死水层"）开两个出口：人审后晋升为 endpoint 资产；重扫时自动 diff 出新路径/消失路径/状态变化。
- **用户故事**：ffuf 扫出 300 条路径，我想把 200/403 的几十个一键晋升进资产树重点测试；下周重扫，我想一眼看到"新增 3 个后台路径、/api/v1/users 状态变了"。
- **与现有功能关系**：补断点（probe-import 有入口无出口）+ 新开 diff 视图；顺带产品化修复 R12（pdb_assets.py:391 与 server.py:542 两处硬编码 scope="in"）。
- **收益 vs 成本**：收益 **高**（修复功能链第一断点，ASM 核心体验就在"观测→实体→变化"）/ 成本 **中**。
- **风险/前提**：晋升门槛直接决定 README:69 既定的"404 灌爆资产树"防线怎么守（见讨论题 2）；diff 依赖两次扫描可比性（同字典同参数）。

### D4 授权范围管理产品化（项目级 scope 清单 + 越界高亮）
- **一句话**：项目里放一份授权目标清单，观测入库自动比对 in/out/unknown，范围外高亮，报告可直接引用授权范围。
- **用户故事**：作为职业测试者，授权边界是合规生命线——任何观测（尤其 probe/recon 结果）自动比对授权清单，范围外的一眼可见，交付报告里能直接引用。
- **与现有功能关系**：增强 + 修复 R12（lint E-105 目前因硬编码 "in" 不可能命中，pentdb.py:239-241）。
- **收益 vs 成本**：收益 **中**（合规价值 + 修复硬伤）/ 成本 **中**。
- **风险/前提**：**与 2026-10-09 用户拍板的"口头授权即开工"极简语义冲突**。PM 立场：R12 本身是一行级 bug（probe scope 缺省改 unknown 或读项目配置），走 bugfix 渠道；**产品化版本必须用户重新拍板，不擅自做**（讨论题 3）。

### D5 报告客户变体（轻量配置，非引擎）
- **一句话**：把硬编码的 pentest/assets 模板（pdb_report.py:44-98）重构为配置驱动（章节开关 + 变量），支持多客户变体与 html/pdf 导出。
- **用户故事**：不同客户/场合要不同报告形态：简洁漏洞单、完整渗透报告、汇报版——一次配置反复用，导出直接发对方。
- **与现有功能关系**：增强（重构 pdb_report.py；出口门禁 lint 与复测计划引用不变）。
- **收益 vs 成本**：收益 **中**（报告是交付门面 + 求职 showcase）/ 成本 **中**。
- **风险/前提**：**模板引擎陷阱**——单用户一个变体可能就够。只做"章节开关+变量"，明确不做通用模板语言（§4）。

### D6 kb 检索增强（语义搜索 / 本地 LLM 问答）
- **一句话**：给 BM25 检索（kb.py:248-265）加向量语义层或本地 LLM 问答。
- **用户故事**：用自然语言问"上次那个 SQL 注入怎么绕 WAF 的"，而不是回忆关键词。
- **与现有功能关系**：增强（BM25 之上加一层）。
- **收益 vs 成本**：收益 **低-中** / 成本 **高**（破坏零依赖纪律，Supabase 侧需 pgvector 或本地嵌入服务）。
- **风险/前提**：**语料规模未核实**（kb 在 Supabase 云端，本地不可见）——个人经验库若仅数十上百条，BM25 远未到失效点。判定为 premature optimization，进"缓做"清单并写明触发条件（§4）。

### D7 外部工具解析器扩展（burp sitemap / nuclei JSON / httpx）
- **一句话**：probe-import 解析器框架（pdb_assets.py:290-308）再加 Burp/nuclei/httpx 输出格式。
- **用户故事**：主力工具是 Burp，sitemap 直接灌库，不用手工导 ffuf。
- **与现有功能关系**：增强（加格式=加纯函数解析器，几十行/格式）。
- **收益 vs 成本**：收益 **中** / 成本 **低**。
- **风险/前提**：低。但每个新解析器都是新的信任面，须守在"工具输出→观测"最小语义内，不引入富特性。

## 3. 推荐排序（Top 3）与理由

| 排序 | 方向 | 核心理由 |
|------|------|---------|
| **1** | **D1 血缘层投产实验** | 产品刚在血缘层下了最重的注（schema v9-v11 + skill 阶段五 + 面板页），却 0 行未验证。PM 第一职责是验证最大未验证假设，而不是继续堆功能。它成本几乎为零（不写代码，跑一个项目），信息价值极高——**用或不用都是决策输入**；且它是差异化叙事"AI 跨会话记忆"的唯一承载，对求职 showcase 有额外权重。 |
| **2** | **D2 复测工作台深化** | 打的是人工投入最大的环节（317 次人审的延续），现有雏形最完整（复测包查看器/lifecycle 联动/时间线都在），增强路径清晰、风险最低。复测质量是产品价值的最终出口——报告只引用 confirmed，confirmed 的可信度由复测保证。 |
| **3** | **D3 探测观测双出口** | 修复功能链第一断点（探测→测试转化），原材料全部就位（probe 层、last_seen/first_seen、用户待办里已有"probe 晋升/变化检测"两条），顺带把 R12 从 bug 修复升级为正确的产品语义。 |

三者关系：D1 决定"要不要继续信血缘层"（验证），D2/D3 分别深化已被证明有人用、有痛点的两个环节（复测、探测）。**没有 D1 之前动工 D4-D7，都是在未验证的地基上继续加层。**

## 4. 不该做 / 缓做清单（防范围蔓延）

| 方向 | 判定 | 理由 |
|------|------|------|
| D6 kb 语义搜索/本地 LLM | **缓做** | 个人语料规模下 BM25 未证明失效；高成本破坏零依赖纪律。触发条件（写进不做清单）：approved 条目规模化（数百+）且 BM25 miss 可被用户感知。 |
| D5 全式模板引擎 | **只做轻量变体** | 单用户场景，Jinja 化是典型过度设计；"章节开关+变量"覆盖 90% 需求。通用模板语言明确不做。 |
| 多项目横向对比视图 | **不做** | 单用户一次做一个 engagement，面板架构是项目域隔离，使用频率存疑。等真实出现"同 CMS 跨三项目"需求再议。 |
| 移动端/远程访问面板 | **不做** | 与"只绑 127.0.0.1 + 无鉴权"的安全姿态（R8，设计内）根本冲突；移动化=绑 0.0.0.0+鉴权体系，是另一个产品决策，不是功能增量。 |
| D4 全量授权范围管理 | **缓做，先修 bug** | 用户已拍板极简授权语义；产品化是产品判断 vs 用户既有决策的冲突，须讨论题 3 拍板后才能进排期。 |

## 5. 讨论题（需用户拍板）

1. **血缘层：推着用起来，还是降级为可选？** 选项 A：下一个真实项目强制挂接 + 设验收标准（如项目结束无孤儿观测比例、intent 覆盖率）；选项 B：承认 9 项目 0 行=设计过重，skill 移除强制、降级为可选（SOP 面板页退役是现成先例）。关键输入只有你有：你的真实工作流里有没有"方向性假设"这个思维习惯？还是习惯打到哪算哪？
2. **probe 晋升门槛用什么规则？** 状态码白名单（200/301/302/401/403）？人审后批量晋升？路径关键词？——这直接决定 README:69 的"404 灌爆"防线怎么守，也决定晋升是半自动还是人审一步。
3. **授权范围要不要借 R12 修复契机产品化？** 做项目级 scope 清单（合规价值+报告可引用授权范围），还是维持"口头授权即开工"极简版、只把 probe scope 硬编码修缺省 unknown？——这是重新审视你 2026-10-09 拍板的机会，也可以选择不拍。
4. **复测轮次要"计划-执行-汇总"三态吗？** 还是保持现在的单 finding 复测 + suggestion 自由文本计划就够？这决定 D2 是做中量级功能还是小增强。
5. **报告形态缺口在哪？** 硬编码 pentest 模板+手工后改（现状）能覆盖你的交付与求职 showcase 吗？最痛的缺口是"多客户变体"还是"导出格式（PDF/HTML）"？——决定 D5 做多深，以及要不要现在就做。

## 补记：假设主权与业界对标（2026-10-12 查证）

**设计语义**：SKILL.md:76「有方向性假设先立意图：`intent add --goal '<方向>' --hypothesis '<依据>'`」是写给 AI 的指令——**intent = AI 提假设**，hint = 人扔线索/判断，plan review = 证伪判定（结论须 refs 引证据）。人立关口（批次对账 / waive 审批 / lifecycle），不立假设。

**业界实证**：
- **XBOW**（自主渗透，$120M C 轮）：coordinator 决策 → 短命攻击 agent → **独立验证器确认可利用性 finding 才上报**；每个 finding 附攻击链 + 可工作 exploit + 完整决策日志；人只控 scope/速率/测试窗口。白皮书案例：agent 从 302 反射参数主动假设开放重定向并验证；「记住同类平台历史 SSRF 漏洞」形成假设挖出 CVE-2025-27888。
- **NodeZero**（Horizon3，$2B）：确定性逻辑防幻觉 + 目标知识图谱 + 攻击链串接 + 证明可利用性 + hack→fix→verify→repeat 持续循环。
- **Intentest**（arXiv 2609.07344，2026）：与 PentDB 血缘层同构——长周期状态外置为持久化「事实-意图 DAG」，意图边受前置事实约束；88.2% vs 基线 44.1%，中高难度轮数 -33%~-48%；命名「上下文遗忘 + 意图漂移」。

**共同模式**：AI 提假设 → AI 执行 → 独立验证 → 全程留痕 → 人只在授权窗口与审批闸门介入。

**对 PentDB 的启示**：
1. 血缘层设计与商业/学术方案同构且多显式人审闸门——**D1 应推着用，不该降级**（0 行是使用问题非设计问题）。
2. 可抄①：finding 显式「假设/已验证」两态，对齐 XBOW validator 分离（现 lint 只查证据完整性，不查可利用性判定）。
3. 可抄②：`intent add` 强制 `kb find-similar`，把历史经验注入假设依据（对齐 XBOW 历史记忆提效案例；修 kb 回路未闭合断点）。
